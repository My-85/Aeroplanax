# Aircraft RL Tuner — 自动化训练调参平台说明书

## 框架架构

```
aircraft-rl-tuner/
│
├── scripts/
│   ├── auto_train_loop.py    (42K) ← 主控循环，唯一入口
│   ├── evaluate_maneuver.py   (21K) ← 评估引擎
│   ├── param_registry.py      (9K)  ← 51个可调参数注册表 [未启用]
│   └── param_applier.py       (10K) ← 正则替换参数工具   [未启用]
│
├── assets/
│   ├── target_metrics_template.json  ← 达标阈值定义
│   ├── latest_eval_report.json       ← 最新评估报告
│   ├── escalation_report.json        ← 停滞升级报告
│   ├── iteration_log.json            ← 历轮记录
│   ├── train_output.log              ← 训练日志
│   ├── claude_code_iter_*.log        ← Claude 每轮输出日志（也作为跨轮记忆）
│   └── backups/iter_N/               ← 每轮代码备份
│
├── references/
│   └── jax_rl_best_practices.md      ← 专家指南（已注入 prompt）
│
被操作的外部文件（Planax/）:
├── envs/reward_functions/full_domain_reward.py     ← 奖励函数（完整传入 prompt）
├── envs/aeroplanax_full_domain_maneuver.py         ← 环境+课程（关键片段传入）
├── envs/termination_conditions/unreach_full_domain.py ← 终止条件（完整传入 prompt）
└── train_full_domain_maneuver_v3.py                ← PPO训练脚本（关键片段传入）
```

## Claude prompt 注入内容

| 内容 | 完整/节选 | 说明 |
|------|-----------|------|
| 奖励函数 full_domain_reward.py | 完整 | ~260行 |
| 终止条件 unreach_full_domain.py | 完整 | ~120行 |
| 环境文件 aeroplanax_full_domain_maneuver.py | 节选 ~75行 | params + on-target + curriculum 三段 |
| 训练脚本 train_full_domain_maneuver_v3.py | 节选 ~65行 | KL/entropy + PPO config |
| 评估报告 JSON | 完整 | 当轮评估结果 |
| 历次迭代摘要 | 完整 | 每轮 success_rate / crash / 修改概述 |
| 上一轮 Claude 完整分析 | 完整（≤3000字） | 跨轮推理记忆 |
| 专家指南 jax_rl_best_practices.md | 完整 | 7.4K 领域知识 |
| 训练日志尾部 | 尾部 2000 字符 | wandb 指标趋势 |

环境和训练脚本只传节选，但 Claude 输出的 `old` 必须精确匹配文件内容，不匹配的编辑会被 `_apply_edits` 安全拒绝。风险在于 Claude 可能基于局部理解做出与未见代码产生逻辑冲突的修改，dry-run 验证可以拦截大部分运行时错误。

```

│    │ (流式)   │   输出: 自然语言分析 + JSON edits       │
│    └────┬─────┘   实时打印Claude思考过程                │
│         ▼                                               │
│    ┌──────────┐   _apply_edits() 字符串替换             │
│    │ 6. 应用  │                                         │
│    └────┬─────┘                                         │
│         ▼                                               │

│    │ 7.Dry-run│   失败 → 回滚 → 给Claude报错再试一次   │

│         ▼                                               │
│    └── 回到 Step 1 ─────────────────────────────────┘   │
└─────────────────────────────────────────────────────────┘
```

## 达标标准

定义在 `assets/target_metrics_template.json`：

| 指标 | 阈值 |
|------|------|
| 总 success_rate | ≥ 0.80 |
| 平均 crash 次数 | ≤ 1.0 / episode |
| 平均 stall 步数 | ≤ 30 |
| Level 1（平飞小转弯） | ≥ 95% |
| Level 2（中等机动） | ≥ 90% |
| Level 3（大转弯+坡度） | ≥ 80% |
| Level 4（激进俯仰+滚转） | ≥ 65% |
| Level 5（极端/倒飞） | ≥ 50% |
| 全域覆盖 | pitch ±70°, roll ±180° |

## 已知局限

1. **环境/训练脚本只传节选** — 奖励和终止条件完整传入，但环境文件(820行)和训练脚本(750行)只传了关键配置段(~140行)。Claude 基于局部理解做的修改可能与未见代码产生逻辑冲突，dry-run 可拦截运行时错误
2. **编辑靠字符串精确匹配** — `_apply_edits()` 用 `str.replace(old, new, 1)`，缩进/空格差一个字符就失败（匹配不到会安全跳过，不会损坏文件）
3. **param_registry / param_applier 未启用** — 已写好 51 个可调参数注册表和正则替换器，但主循环依赖 Claude 自由编辑模式，未接入结构化参数调优

## 操作说明

### 环境变量

```bash
# 必须设置
export ANTHROPIC_AUTH_TOKEN=<你的API密钥>
export ANTHROPIC_BASE_URL=https://linoapi.com.cn

# 可选：切换 Claude 调参用的模型（默认 opus）
export ANTHROPIC_TUNER_MODEL=claude-opus-4-6            # 默认（强推理，适合难任务）
export ANTHROPIC_TUNER_MODEL=claude-sonnet-4-20250514   # 可选（便宜快，适合简单调参）
```

### 基本启动

```bash
cd /home/dqy/aeroplanax/new/20251215最新代码库/aircraft-rl-tuner/scripts

# 从头训练（完整循环）
python auto_train_loop.py --max-iters 10 --eval-episodes 50

# 从已有 checkpoint 开始（跳过第一轮训练，直接评估）
python auto_train_loop.py --checkpoint /path/to/checkpoint_epoch_1600 --max-iters 5

# 只评估+调参，不启动训练（用最新checkpoint）
python auto_train_loop.py --skip-training --max-iters 3
```

### 命令行参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `--max-iters` | 10 | 最大迭代轮数 |
| `--checkpoint` | 无 | 指定起始 checkpoint（跳过首轮训练） |
| `--skip-training` | 关 | 不启动训练子进程，只评估+调参 |
| `--eval-episodes` | 2 | 每轮评估集数 |
| `--param-stall-limit` | 3 | 连续多少轮无进展触发停滞通知 |
| `--target-metrics` | assets/target_metrics_template.json | 达标阈值文件 |

### 停滞后恢复

当连续 3 轮所有指标（success_rate + crash + reward）均无进展时，循环暂停并输出通知：

```
╔════════════════════════════════════════════════════════════╗
║  ⚠ 参数调优已连续 3 轮无明显进展，需要代码级修改         ║
║  请使用 Claude Code 进行代码级修改                       ║
╚════════════════════════════════════════════════════════════╝
```

此时你可以：
1. 用 Claude Code 手动分析和修改代码
2. 查看 `assets/escalation_report.json` 了解详情
3. 修改完后继续：
```bash
python auto_train_loop.py --checkpoint <报告中的checkpoint路径>
```

❯ 那现在我这个自动化训练框架是不是只能调调参数了？对于代码本身env\reward设计\task设计\课程设计 
等等造成的RL baseline训不出来就束手无策了？                                                    
                                                                                               
● 不是只能调参数。你现在的框架可以做代码修改——前 3 轮 Claude                                   
  实际上改了课程难度、奖励系数、终止条件阈值、初始条件范围，这些都是代码级的改动，不是纯调参。 
                                                                                               
  但你的直觉是对的——它能改的深度有限。                                                         
                                                                                               
  当前框架能做 vs 不能做                                                                       
                                                                                               
  能做（字符串替换范围内）：          不能做：                                                 
  ├─ 改数值参数                       ├─ 新增一个完整的 reward 组件函数                        
  ├─ 改 reward 的权重/阈值            ├─ 重新设计观测空间（改 obs 维度）                       
  ├─ 改课程的难度梯度                 ├─ 增加新的 termination 条件                             
  ├─ 改终止条件的阈值                 ├─ 重构课程逻辑（比如从线性改为树形）                    
  ├─ 小范围重写某个表达式             ├─ 修改环境动力学（飞行器模型）                          
  └─ 替换几行连续代码                 ├─ 添加新文件                                            
                                      ├─ 跨文件协调修改（改 obs 空间需要                       
                                      │   同时改 env + reward + train）                        
                                      └─ 需要先 debug 再改的问题                               
                                                                                               
  前 3 轮全部 0% success rate 就是最好的证明 — 在当前 reward/env                               
  架构根本跑不通的情况下，调参数和小修改解决不了问题。                                         
                                                                                               
  但这不是 SDK 的锅 — CLI 也一样                                                               
                                                                                               
  你之前用 CLI + tool use 方案时，Claude 有 Read/Edit/Bash                                     
  全套工具，理论上能做深度修改。但实际上：                                                     
                                                                                               
  1. Claude 通过 API 调用时，没有你在终端交互时给它的那种详细上下文和反复引导                  
  2. 自动化 prompt 是固定模板，不像你手动对话时能反复追问                                      
  3. Claude 做完一轮修改就结束了，不能像交互模式那样"跑一下看看 → 再改 → 再跑"                 
                                                                                               
  所以问题的本质不是 SDK vs CLI，而是：单轮自动化 vs 多轮人机交互。

  实际的解决思路

  你的框架已经有停滞升级机制——连续 N 轮没进展就暂停通知你。这个设计是对的。实际工作流应该是：

    ┌─────────────────────────────────────────────────┐
  │  自动循环（SDK 单轮）                            │
  │  能处理: 参数调优、小范围代码修改                │
  │  每轮: 训练→评估→Claude分析→改代码→验证          │
  │                                                  │
  │  连续 3 轮无进展                                 │
  │         │                                        │
  │         ▼                                        │
  │  ╔════════════════════════════╗                   │
  │  ║  停滞 → 暂停自动循环       ║                   │
  │  ╚════════════════════════════╝                   │
  │         │                                        │
  │         ▼                                        │
  │  你打开终端，用 Claude Code 交互式介入            │
  │  能处理: 重新设计 reward、重构课程、改 obs 空间   │
  │  你: "分析一下为什么 baseline 跑不通"             │
  │  Claude: 读代码 → 分析 → 提方案 → 你确认 → 改    │
  │  你: "跑一下看看效果"                             │
  │  Claude: 执行训练 → 看结果 → 继续调整             │
  │         │                                        │
  │         ▼                                        │
  │  改完后，重启自动循环继续精调                     │
  │  python auto_train_loop.py --checkpoint <ckpt>   │
  └─────────────────────────────────────────────────┘

  这就是你应该用的工作模式：自动循环做精调，人机交互做架构级改动。

  你现在的框架不需要大改。真正要做的是：用 Claude Code（就是你现在终端里用的这个）交互式地把
  baseline 先调通，让 success_rate 至少到 30%+，然后自动循环才有意义去做后续精调。
